        PART 2 — CRITICAL BLOCKERS (fix before ANY public launch or sale)
-----------------------------------------------------------------------------------

--- A. SECURITY: HARDCODED ADMIN CREDENTIALS IN SOURCE CONTROL ---------------------
  A1. backend/src/TuitionPlatform.Api/Program.cs contains a real admin email and
      the plaintext password "Martin#123", committed to git. Anyone with repo
      access — or anyone who ever forks/clones it — owns your production admin
      account.
  A2. Worse: the startup block RE-HASHES AND OVERWRITES that password on EVERY
      application start. If you change your admin password in the UI, the next
      deploy silently resets it back. You can never actually secure this account.
  FIX: Move the seed email/password to environment variables. Only create the
      admin if missing; never overwrite an existing password. Rotate the current
      password immediately, and treat "Martin#123" as permanently compromised
      since it is in git history.

--- B. SECURITY: CORS ALLOWS EVERY ORIGIN, WITH CREDENTIALS ------------------------
  B1. Program.cs sets .SetIsOriginAllowed(origin => true) together with
      .AllowCredentials() — in ALL environments, not just development (the code
      comment says "development" but there is no environment check around it).
      Any website on the internet can call your API in a logged-in user's
      browser context.
  FIX: Read an allow-list of origins from configuration. Permissive CORS only
      inside app.Environment.IsDevelopment().

--- C. BUSINESS LOGIC: THE COMMISSION PAYWALL IS BYPASSABLE ------------------------
  C1. THE BIGGEST FUNCTIONAL BUG IN THE SYSTEM.
      There are TWO implementations of "get my applications":
        - ApplicationWorkflowService.GetMyApplicationsAsync()  -> masks the
          parent's phone number as "********" unless payment is verified. Correct.
        - TeacherService.GetMyApplicationsAsync()              -> maps the DTO
          directly with NO masking at all.
      TeachersController's GET /api/teachers/applications is wired to the SECOND,
      UNMASKED one. A teacher calls that endpoint and receives every parent's
      real phone number for free — completely bypassing the commission model
      that the entire business depends on.
  C2. Compounding this: ApplicationWorkflowService.VerifyPaymentAsync() — the
      admin action that is supposed to UNLOCK contact details after payment —
      is not exposed by any controller. So the legitimate unlock path doesn't
      work, while the illegitimate one does.
  FIX: Delete the duplicate unmasked method from TeacherService (or make it
      delegate to the masking one), route the controller to the masked
      implementation, and add POST /api/applications/{id}/verify-payment
      for Admin.

--- D. THE PARENT ROLE DOES NOT EXIST ----------------------------------------------
  D1. Domain/Enums/UserRole.cs defines only { Teacher = 1, Admin = 2 }.
  D2. But five endpoints already carry [Authorize(Roles = "Parent")] —
      all four DemoController parent endpoints, GET /api/payments/parent, and the
      class-level attribute on ApplicationsController. Every one of them is
      permanently unreachable dead code.
  D3. ParentProfile.cs exists as an entity but has no DbSet, no EF
      configuration, no repository, and no migration — it is not in the database.
  D4. No POST /api/auth/parent/register endpoint and no RegisterParentAsync in
      AuthService.
  D5. Frontend: RegisterParentPage.jsx is not routed, and calls a nonexistent
      authApi.registerParent function.
  Net effect: your "two-sided marketplace" has one side. Full fix plan in Part 4A.

--- E. SESSIONS DIE AND CANNOT REFRESH --------------------------------------------
  E1. The backend implements POST /api/auth/refresh correctly and returns a
      refresh token on login. The frontend stores it in localStorage and then
      NEVER USES IT. apiClient.js literally contains the comment "We could add
      refresh token logic here if needed."
  E2. On any 401, apiClient immediately dispatches logout(). So the moment an
      access token expires, the user is kicked out mid-task with no warning.
  FIX: Add a response interceptor that, on 401, calls /auth/refresh once, retries
      the original request, and only logs out if the refresh itself fails.
      Guard against concurrent refresh storms with a single in-flight promise.

              PART 3 — BROKEN, HALF-BUILT, OR DEAD FEATURES
-----------------------------------------------------------------------------------
  1.  AutoApproveTeachers setting is dead. It exists in AdminSettings, is
      editable in the admin UI, and is returned by GET /api/admin/settings —
      but AuthService.RegisterTeacherAsync hardcodes IsApproved = false and
      never reads it. Toggling it in the UI does nothing.

  2.  Unapproved teachers can still apply to posts. TeacherService.
      ApplyToPostAsync never checks profile.IsApproved. The entire approval
      workflow can be skipped.

  3.  Teachers can apply to the same post unlimited times. No duplicate check
      in ApplyToPostAsync — a teacher can spam a parent's inbox with 100
      applications to one post.

  4.  Anyone can message anyone. MessageService.SendMessageAsync only checks
      that both users exist. There is no check that they share an application,
      post, or demo. A teacher can DM every parent on the platform directly —
      another route around the commission paywall, and an open spam channel.

  5.  Message.IsRead is never set to true anywhere in the codebase. There is no
      mark-as-read endpoint, no unread count, and no inbox/conversation-list
      endpoint. You can only open a chat if you already know the other person's
      GUID — the messaging feature has no entry point.

  6.  Teachers self-certify payment. POST /api/payments/{id}/pay lets a teacher
      set their own payment to Paid with a free-text reference. No admin
      approval, no proof, no verification. Combined with C1, commission is
      effectively optional.

  7.  No payment state-machine guard. MarkAsPaidAsync will happily re-mark an
      already-Paid or Refunded payment as Paid again.

  8.  GET /api/tuition-posts/pending is hardcoded to return an empty list, and
      POST /{id}/approve is marked "deprecated" in a code comment — yet the
      admin UI still has a PendingPostsPage.jsx wired to them. That admin screen
      is permanently blank by design.

  9.  Post status model is inconsistent. TuitionPostStatus has Pending/Approved/
      Open/Closed, but CreateAsync always writes Open, the Pending query returns
      nothing, and ApplyToPostAsync checks for "Approved OR Open". Two of the
      four states are unreachable. Decide on the real lifecycle and delete the rest.

  10. FeatureTeacher is one-way. AdminService.FeatureTeacherAsync only ever sets
      IsFeatured = true. There is no un-feature action. Also, a whole
      FeaturedTeacher entity exists but is never used by this code path.

  11. RemoveTeacherAsync is a hard delete with no soft-delete flag. Payments and
      applications reference that teacher; the FKs use DeleteBehavior.Restrict,
      so this will either throw at runtime or destroy financial history.

  12. UpdateUserRoleAsync has no guardrails. An admin can demote themselves, and
      nothing prevents removing the last remaining admin — locking everyone out.

  13. Approved teachers can silently change their identity. UpdateProfileAsync
      lets a teacher rewrite qualifications, subjects, and experience after
      approval without resetting IsApproved or notifying an admin.

  14. AdminService.GetTeacherDetailsAsync fetches the profile via GetByIdAsync,
      which does NOT .Include(t => t.User). Any mapping that reads User.FullName
      or User.Email will come back null on the admin teacher-details screen.

  15. Leftover scaffolding: Class1.cs still present in Domain, Application, and
      Infrastructure projects.

                PART 5 — MAKING THE SYSTEM TRULY DYNAMIC
-----------------------------------------------------------------------------------
You asked specifically for a "totally dynamic" system. Here is what is currently
hardcoded or unmanageable, and what to do about it.

  [ ] SUBJECTS, CLASSES, AND BOARDS ARE FREE-TEXT STRINGS.
      TeacherProfile.Subjects and .Classes are comma-ish strings; TuitionPost
      uses free-text Subject/ClassLevel. This is why search uses .Contains()
      and why "Maths"/"Mathematics"/"maths " are three different subjects.
      FIX: Subject, Board, and ClassLevel lookup tables + join tables, managed
      from an admin screen, served to the frontend as dropdown data via API.
      This single change fixes search quality, filtering, and analytics at once.

  [ ] CITIES AND AREAS ARE FREE-TEXT. Same problem — breaks location filtering
      and makes "teachers in Delhi" unreliable. Needs a managed location table.

  [ ] LANDING PAGE CONTENT IS HARDCODED IN JSX. Hero copy, testimonials,
      featured teachers, FAQ, stats — all require a code deploy to change.
      FIX: a small CMS-style content API + admin editor, following the same
      pattern AdminSettings already uses successfully.

  [ ] NO FEATURE FLAGS. No way to turn a feature on/off per environment or roll
      one out gradually. Add a simple flags table + config endpoint.

  [ ] EMAIL/SMS TEMPLATES should be data, not hardcoded strings, so you can edit
      wording without a deploy.

  [ ] WHAT IS ALREADY DONE RIGHT: AdminSettings (commission percentage, flat
      amount, payment instructions) is exactly the right pattern — admin-editable
      business config read at runtime. Extend that pattern everywhere above.
      (Just make sure the settings you expose actually get read — see Part 3
      item 1, where AutoApproveTeachers is editable but ignored.)

                    PART 6 — PERFORMANCE & SCALE
-----------------------------------------------------------------------------------
These are fine at 50 users and fatal at 5,000. Worth fixing before you demo the
platform to a buyer with a seeded database.

  [ ] PAGINATION IS FAKE ACROSS THE WHOLE SYSTEM. SearchService, TuitionPost-
      Service.GetMyPostsAsync, and GetAllPostsAsync all load EVERY matching row
      from the database with .ToListAsync() and then apply .Skip()/.Take() in
      C# memory. Page 1 of 10 results costs you the entire table.
      FIX: push Skip/Take into the IQueryable before it hits the database.

  [ ] ADMIN DASHBOARD LOADS FOUR ENTIRE TABLES TO PRODUCE SEVEN NUMBERS.
      GetDashboardAsync pulls all users, all posts, all payments, and all
      teacher profiles into memory just to .Count() them.
      FIX: use CountAsync()/SumAsync() database aggregates.

  [ ] GET /api/admin/users, /admin/teachers, /admin/applications have NO
      pagination at all. These will time out.

  [ ] ONLY THREE DATABASE INDEXES EXIST in the entire schema (User.Email,
      RefreshToken(UserId,Token), Message.ConversationKey). Missing indexes on
      columns queried constantly:
        TeacherProfile   : IsApproved, City, Area, UserId
        TuitionPost      : Status, City, CreatedByUserId, CreatedAtUtc
        TeacherApplication: TeacherProfileId, TuitionPostId, Status
        Payment          : TeacherId, ParentId, Status
      Add these in a migration — it is a cheap, large win.

  [ ] NO RESPONSE CACHING on public endpoints (/tuition-posts/open,
      /search/teachers) — every anonymous visitor hits the database directly.

  [ ] NO ASYNC/BACKGROUND JOB INFRASTRUCTURE. Once emails and SMS exist, they
      must not run inline in the request. Add Hangfire or a hosted background
      service before wiring notifications.

  [ ] FRONTEND: no code splitting or lazy loading of routes; no image
      optimization; the whole admin bundle ships to anonymous visitors.

              PART 7 — SECURITY, COMPLIANCE, AND OPERATIONS

SECURITY (beyond the Part 2 blockers)
  [ ] NO RATE LIMITING anywhere. /api/auth/login can be brute-forced without
      limit. .NET 8 has AddRateLimiter built in — apply it globally and
      aggressively on auth endpoints.
  [ ] NO ACCOUNT LOCKOUT after repeated failed logins, and no CAPTCHA.
  [ ] NO PASSWORD RESET / FORGOT PASSWORD FLOW AT ALL. A user who forgets their

  [ ] NO EMAIL VERIFICATION FLOW. User.EmailVerified exists and is always false

  [ ] LOGIN LEAKS ACCOUNT EXISTENCE. AuthService throws NotFoundException("User")

      wrong password — so an attacker can enumerate which emails are registered.
      Return one identical error for both cases.
  [ ] NO LOGOUT / REFRESH-TOKEN REVOCATION endpoint. Tokens stay valid after
      the user "logs out" client-side.
  [ ] RequireHttpsMetadata = false is set unconditionally in Program.cs.
  [ ] TOKENS IN localStorage are XSS-readable. Acceptable for now, but

  [ ] NO SECRET SCAN of git history. Given Part 2 A1, do one.
